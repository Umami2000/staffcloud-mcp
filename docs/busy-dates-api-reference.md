# StaffCloud Busy Dates API — Reference for App Integration

> Tested live against `testreon.staff.cloud` on 2026-04-01.
> This doc covers **reading** busy dates only. The POST (create) endpoint is currently broken (returns 500 after passing validation).

---

## Endpoint

```
GET /api/v1/busy-dates
```

**Auth**: `Authorization: Bearer <JWT_TOKEN>`

---

## Full Record Structure

Every busy date record has this shape:

```json
{
  "id": 30,
  "employee_id": 16,
  "start": "2026-04-02 00:00:00",
  "end": "2026-04-02 23:59:59",
  "type": "vacation",
  "reason": "Ferien",
  "description": "Ferien",
  "busy_entry": {
    "id": 1,
    "creator_entity_relation_id": 8696,
    "type": "vacation",
    "description": "Ferien",
    "start_date": "2026-02-02",
    "start_time": null,
    "end_time": null,
    "repeats_configuration": {
      "repeatsBase": "week",
      "repeatsAmount": 1,
      "repeatsOn": [1, 2],
      "endMode": "date",
      "endValue": "2026-03-05"
    }
  },
  "files_ids": []
}
```

### Field Reference

| Field | Type | Description |
|-------|------|-------------|
| `id` | integer | Unique busy date record ID |
| `employee_id` | integer | The employee this busy date belongs to |
| `start` | datetime | Start of unavailability (`"YYYY-MM-DD HH:MM:SS"`) |
| `end` | datetime | End of unavailability (`"YYYY-MM-DD HH:MM:SS"`) |
| `type` | string enum | Category of unavailability (see Type Values below) |
| `reason` | string | **DEPRECATED** — use `type` + `description` instead |
| `description` | string | Free-text description (may be empty `""`) |
| `busy_entry` | object | Internal scheduling metadata (see below) |
| `files_ids` | integer[] | Attached file IDs (e.g. doctor's note) |

### `busy_entry` Sub-Object

| Field | Type | Description |
|-------|------|-------------|
| `id` | integer | Internal busy entry ID (groups recurring entries) |
| `creator_entity_relation_id` | integer | Who created this entry |
| `type` | string | Same as top-level `type` |
| `description` | string | Same as top-level `description` |
| `start_date` | date string | Date part only (`"YYYY-MM-DD"`) |
| `start_time` | time/null | Time part for partial-day entries (`"06:00:00"`) or `null` for all-day |
| `end_time` | time/null | Time part for partial-day entries (`"16:00:00"`) or `null` for all-day |
| `repeats_configuration` | object/null | Recurrence rules (null = one-off, object = recurring) |

### `repeats_configuration` Sub-Object (when not null)

| Field | Type | Description |
|-------|------|-------------|
| `repeatsBase` | string | Recurrence unit: `"week"`, `"month"`, etc. |
| `repeatsAmount` | integer | Recurrence interval (e.g. `1` = every week) |
| `repeatsOn` | integer[] | Days of week (1=Monday, 2=Tuesday, ..., 7=Sunday) |
| `endMode` | string | `"date"` (ends on specific date) or `"count"` |
| `endValue` | string | End date `"YYYY-MM-DD"` or occurrence count |

## Type Values (Enum)

| `type` value | Display Label | All-Day? | Notes |
|-------------|---------------|----------|-------|
| `vacation` | Vacation / Ferien | Usually yes | Most common type |
| `sick_leave` | Sick leave | Usually yes | |
| `paid_training` | Paid training | Usually yes | |
| `parental_leave` | Parental leave | Usually yes | |
| `compensation_time` | Compensation time | Usually yes | Time-off for overtime |
| `day_off` | Day Off | Yes | |
| `no_show` | No Show | **No** — has specific times | Auto-generated by Pre-Check-In system |
| `other` | Other | Usually yes | `description` field contains the reason |

### How to detect all-day vs partial-day

```
if (busy_entry.start_time === null && busy_entry.end_time === null) → all-day
if (busy_entry.start_time !== null) → partial-day (use start_time + end_time)
```

Or equivalently from the top-level fields:
```
All-day:     start = "2026-04-02 00:00:00", end = "2026-04-02 23:59:59"
Partial-day: start = "2026-04-01 06:00:00", end = "2026-04-01 16:00:00"
```

## Query Parameters

### `fields` — Select specific fields (reduces payload)

```bash
GET /busy-dates?fields=id,employee_id,start,end,type,description
```

**Available fields**: `id`, `employee_id`, `start`, `end`, `type`, `reason`, `description`, `busy_entry`, `files_ids`

> When using `fields`, the `busy_entry` object is omitted unless you include it.
> The `busyDatesEmployee` embed is also omitted unless you include it AND use `embed`.

### `employee_id` — Filter by employee

```bash
# Single employee
GET /busy-dates?employee_id=6

# Multiple employees (comma-separated)
GET /busy-dates?employee_id=6,16
```

### `type` — Filter by busy date type

```bash
GET /busy-dates?type=vacation
GET /busy-dates?type=sick_leave
```

### `sort` — Sort results

```bash
# Chronological (ascending)
GET /busy-dates?sort=start

# Reverse chronological (descending)
GET /busy-dates?sort=-start
```

### `embed` — Include related employee data

```bash
GET /busy-dates?embed=busyDatesEmployee
```

Adds a `busyDatesEmployee` array (always contains exactly 1 element) with the **full employee record** including PII (name, email, phone, address, birthday, gender, qualifications, etc).

### `envelope` — Wrap response

```bash
GET /busy-dates?envelope=true
# Returns: {"response": [...]}
```

## Date Filtering — CRITICAL QUIRKS

> **The `/busy-dates` endpoint does NOT support the same filter operators as `/events`.**
> This was verified by live testing — some operators silently return `[]`.

### What WORKS

| Filter | Example | Result |
|--------|---------|--------|
| **Exact match** | `start=2026-04-02 00:00:00` | Records with that exact start datetime |
| **Greater than** `>` | `start=>2026-04-01` | Records starting after April 1 |
| **Less than** `<` | `end=<2026-04-03` | Records ending before April 3 |
| **Like/partial** `~` | `start=~2026-04` | Records with start containing "2026-04" |
| **Combined gt+lt** | `start=>2026-04-01&end=<2026-04-05` | Date range (see examples) |

### What DOES NOT WORK (silently returns `[]`)

| Filter | Example | Result |
|--------|---------|--------|
| `<=` (less-than-or-equal) | `start=<=2026-04-04 23:59:59` | **Returns `[]`** |
| `>=` (greater-than-or-equal) | `start=>=2026-04-01` | **Returns `[]`** |

### Recommended: Use `start=>` to Skip Old Data

The simplest and most practical approach: use `start=>YYYY-MM-DD` (strict greater-than, offset by 1 day) to skip old history. Then do a precise overlap check client-side if needed.

```bash
# "Give me all busy dates from April onward" — skips all old Feb/March data
GET /busy-dates?start=>2026-03-31&fields=id,employee_id,start,end,type,description
```

> Use the day **before** your actual start date because `>` is strict (excludes the boundary).

### Other Strategies

**Strategy 1: Like filter on month (best for calendar views)**
```bash
# All busy dates in April 2026
GET /busy-dates?start=~2026-04&fields=id,employee_id,start,end,type
```

**Strategy 2: Greater-than + less-than (for specific ranges)**
```bash
# April 2-4: start > April 1 AND end < April 5
GET /busy-dates?start=>2026-04-01&end=<2026-04-05&fields=id,employee_id,start,end,type
```

> **Note**: Strategy 2 uses strict `>` / `<` (not `>=` / `<=`).
> To include the boundary dates, offset by one day:
> - To include April 2: use `start=>2026-04-01` (day before)
> - To include April 4: use `end=<2026-04-05` (day after)

**Strategy 3: Fetch all + client-side filter (most reliable)**
```bash
# Fetch everything, filter in your app code
GET /busy-dates?fields=id,employee_id,start,end,type,description
```
Then in your app:
```typescript
const rangeStart = new Date("2026-04-02 00:00:00").getTime();
const rangeEnd = new Date("2026-04-04 23:59:59").getTime();
const filtered = busyDates.filter(b => {
  const bStart = new Date(b.start).getTime();
  const bEnd = new Date(b.end).getTime();
  return bStart <= rangeEnd && bEnd >= rangeStart; // overlap check
});
```

**Strategy 4: Filter by employee IDs (best when you know who)**
```bash
GET /busy-dates?employee_id=6,16,3&fields=id,employee_id,start,end,type
```

```bash
curl -s 'https://YOURCOMPANY.staff.cloud/api/v1/busy-dates?fields=id,employee_id,start,end,type,description' \
  -H 'Authorization: Bearer YOUR_TOKEN'
```

### Fetch busy dates for specific employee
```bash
curl -s 'https://YOURCOMPANY.staff.cloud/api/v1/busy-dates?employee_id=6&fields=id,employee_id,start,end,type,description&sort=start' \
  -H 'Authorization: Bearer YOUR_TOKEN'
```

### Fetch busy dates for a month (calendar view)
```bash
curl -s 'https://YOURCOMPANY.staff.cloud/api/v1/busy-dates?start=~2026-04&fields=id,employee_id,start,end,type,description&sort=start' \
  -H 'Authorization: Bearer YOUR_TOKEN'
```

### Fetch busy dates for a date range
```bash
# April 2-4, 2026 (use day before/after for boundary inclusion)
curl -s -G 'https://YOURCOMPANY.staff.cloud/api/v1/busy-dates' \
  --data-urlencode 'start=>2026-04-01' \
  --data-urlencode 'end=<2026-04-05' \
  --data-urlencode 'fields=id,employee_id,start,end,type,description' \
  --data-urlencode 'sort=start' \
  -H 'Authorization: Bearer YOUR_TOKEN'
```

### Fetch only sick leaves
```bash
curl -s 'https://YOURCOMPANY.staff.cloud/api/v1/busy-dates?type=sick_leave&fields=id,employee_id,start,end,type,description' \
  -H 'Authorization: Bearer YOUR_TOKEN'
```

### Fetch with full employee data embedded
```bash
curl -s 'https://YOURCOMPANY.staff.cloud/api/v1/busy-dates?employee_id=6&embed=busyDatesEmployee' \
  -H 'Authorization: Bearer YOUR_TOKEN'
```

## Overlap Detection (for Schedule Matching)

To check if a busy date conflicts with an event/shift, use the **interval overlap formula**:

```
overlap = (busy.start <= event.end) AND (busy.end >= event.start)
```

### TypeScript Implementation

```typescript
interface BusyDate {
  id: number;
  employee_id: number;
  start: string;       // "YYYY-MM-DD HH:MM:SS"
  end: string;         // "YYYY-MM-DD HH:MM:SS"
  type: "vacation" | "sick_leave" | "paid_training" | "parental_leave"
       | "compensation_time" | "day_off" | "no_show" | "other";
  description: string;
}

interface Event {
  id: number;
  start: string;
  end: string;
}

function findConflictingBusyDates(
  busyDates: BusyDate[],
  event: Event,
  employeeId: number
): BusyDate[] {
  const eStart = new Date(event.start).getTime();
  const eEnd = new Date(event.end).getTime();

  return busyDates.filter(b =>
    b.employee_id === employeeId &&
    new Date(b.start).getTime() <= eEnd &&
    new Date(b.end).getTime() >= eStart
  );
}
```

### Example: Annotating a Schedule

```typescript
// 1. Fetch events for April 2-4
const events = await fetchEvents("2026-04-02", "2026-04-04");

// 2. Fetch assignments for those events
const assignments = await fetchAssignments(events.map(e => e.id));

// 3. Fetch ALL busy dates (client-side filtering is most reliable)
const busyDates = await fetch(
  `${API_URL}/busy-dates?fields=id,employee_id,start,end,type,description`
).then(r => r.json());

// 4. For each assigned employee on each event, check for conflicts
for (const event of events) {
  for (const assignment of assignments.filter(a => a.event_id === event.id)) {
    const conflicts = findConflictingBusyDates(
      busyDates,
      event,
      assignment.employee_id
    );
    if (conflicts.length > 0) {
      // This employee has a busy date overlapping this shift
      // Show the red icon in your UI
      assignment.busy_date = {
        type: conflicts[0].type,
        description: conflicts[0].description,
      };
    }
  }
}
```

## Known API Limitations

1. **CREATE is broken** — POST `/busy-dates` returns 500 after validation passes. The API requires a `time` object with `mode: "full_day" | "interval"`, but then crashes internally. Create busy dates through the StaffCloud UI instead.

2. **No `<=` / `>=` operators on dates** — Unlike `/events`, the `/busy-dates` endpoint silently ignores `<=` and `>=` comparison operators and returns `[]`. Use `>` / `<` (strict) or `~` (like) or fetch all + filter client-side.

3. **`reason` field is deprecated** — Always use `type` (enum) + `description` (free text). The `reason` field duplicates `description` and will be removed.

4. **Recurring entries are expanded** — A single recurring busy entry (e.g. "vacation every Mon+Tue") is expanded into individual records per occurrence. They share the same `busy_entry.id` but have different top-level `id` values and dates.

5. **No pagination** — The endpoint returns all records. For large tenants, always use `fields` to reduce payload size.
